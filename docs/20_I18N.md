# 20 — Internationalization & Localization Architecture

## 20.1 Principle: Translation Keys Everywhere, No Hardcoded Text

Every user-visible string in the system — UI labels, validation messages, error messages, email/SMS templates, booking/cancellation/payment messages, room type and amenity names, SEO metadata, page titles/descriptions, legal document references — is resolved through a **translation key**, never a hardcoded literal string in source code. This is a hard engineering rule enforced by lint/CI checks (flag any raw string literal rendered to a user-facing surface) rather than left to developer discipline alone, because retrofitting this after the fact across a growing codebase is far more expensive than enforcing it from the first commit.

## 20.2 Supported Locales

`AZ, EN, RU, TR, DE, ES` — all six are **technically supported** (translation infrastructure, database taxonomy translations, email/SMS templates, date/number/currency formatting) from V1. This does **not** mean all six are marketing-active at launch — see 20.7.

## 20.3 Translation Storage & Delivery

- **UI strings**: key-value translation files (e.g. JSON/ICU MessageFormat) per locale, loaded by the frontend framework's i18n library — supports pluralization rules (which differ meaningfully between English, Russian, and Azerbaijani) and interpolation (e.g. "You have {count} upcoming bookings").
- **Data-driven taxonomy** (`RoomType`, `Amenity` — `09_DOMAIN_MODEL.md`): each taxonomy row has a `translation_key`, resolved against the same translation store — so "Training Room" / "Təlim otağı" / "Тренинг-зал" / "Eğitim odası" all resolve from one canonical `RoomType` ID, never duplicated as separate rows per language.
- **Transactional content** (emails/SMS, `17_NOTIFICATION_ARCHITECTURE.md`): templates keyed the same way, resolved at send time to the recipient's stored `User.locale`.
- **User-generated content** (room descriptions, reviews): stored as-authored in whatever language the provider/customer wrote it — **not machine-translated in V1** (translation-key infrastructure covers platform copy, not arbitrary free text; automated UGC translation is a plausible V2 feature, not built now).

## 20.4 Currency & Locale Architecture

- **Default currency: AZN.** Every `Room.base_price` and all monetary fields are currency-aware (`10_DATABASE_SCHEMA.md` §10.2 — integer minor units + ISO 4217 currency code), so adding `EUR`, `TRY`, `GEL` for future markets is a data/configuration change, not a schema change.
- **Locale ≠ currency**: a Russian-speaking user browsing in `RU` locale viewing a Baku listing still sees the price in `AZN` — currency is tied to the **listing's market**, not the viewer's language preference, since language and the actual price the provider set are independent concerns. (A future multi-currency *display* conversion, e.g. showing an approximate EUR equivalent for a foreign visitor, is a clearly-labeled-as-estimate V2 nicety, not a V1 requirement.)
- **Number/date formatting**: locale-aware formatting (decimal separators, date order, calendar week-start day) applied via standard `Intl`-family APIs, not hand-rolled formatting logic.

## 20.5 Validation & Error Messages

Server-side validation error codes (`11_API_CONTRACTS.md` — machine-readable `code` field) are mapped to localized messages on the **frontend**, not returned pre-localized from the backend — this keeps the API contract locale-agnostic and cacheable, and means adding a 7th language later never requires a backend deployment, only a new translation file.

## 20.6 Right-to-Left and Character Set Considerations

None of the six launch languages are RTL, but component layout (`08_DESIGN_SYSTEM.md`) is built RTL-safe as a low-cost precaution for potential future market expansion. Azerbaijani's Latin-extended characters (Ə/ə, Ğ/ğ, etc.) and Cyrillic (Russian) both need explicit font/encoding verification — flagged as a concrete pre-launch QA checklist item, not assumed to "just work" because a typeface renders basic Latin correctly.

## 20.7 Launch Language Strategy (Technical Readiness ≠ Marketing Activation)

| Locale | Technical support | Content-active at launch | Rationale |
|---|---|---|---|
| AZ | ✅ | ✅ | Primary market language |
| EN | ✅ | ✅ | International remote workers, foreign visitors, credibility signal |
| RU | ✅ | ✅ | Widely used as a second language in the target market and region |
| TR | ✅ | Deferred | Relevant for future Turkey expansion (`02_MARKET_RESEARCH.md`) and some current cross-border business; not worth SEO/content investment until AZ traction is proven |
| DE | ✅ | Deferred | Relevant for European business travelers/expansion; low near-term AZ search volume |
| ES | ✅ | Deferred | Lowest near-term relevance to AZ launch; kept technically ready for later markets |

This distinction (all six technically supported vs. three content-active) is what satisfies both the brief's "system supports all six from day one" requirement and the practical reality that translating and SEO-optimizing content for near-zero-traffic languages before launch is wasted effort better spent on the three languages actually driving early usage.

## 20.8 Language Switcher UI Shows All Six From Launch (Mandatory)

**Status: mandatory rule for all frontend implementation from Phase 4 onward** (recorded before frontend code existed, so this refines rather than reworks the plan above — §20.7's content-activation/SEO investment strategy is unchanged).

§20.7's "content-active at launch" column governs SEO/marketing investment (which locales get translated content and search-engine optimization work first), **not** which locales the UI lets a visitor pick. The header language switcher is a single compact dropdown exposing **all six** locales at launch — 🇦🇿 AZ, 🇷🇺 RU, 🇬🇧 EN, 🇹🇷 TR, 🇪🇸 ES, 🇩🇪 DE — every time, not three now and three added later:

- Shows the current locale in the trigger; the open dropdown marks the active selection visually distinct from the other five.
- Selecting a locale switches the UI immediately (no page reload required) and persists the choice (`User.locale` for an authenticated user, a cookie/localStorage fallback for an anonymous visitor — same mechanism the theme preference uses, §8.5).
- Usable on mobile at the same breakpoints as §8.6 — a native `<select>`-style or custom dropdown that doesn't require desktop-precision pointing.
- Every string resolves through a translation key per §20.1 regardless of whether that locale is "content-active" — a deferred locale (TR/DE/ES) that is missing a specific translated string falls back to EN for that string rather than showing a raw key or blank text, so the switcher is always safe to expose even before a locale's content work is finished.
- This requires no new architecture: §20.2 already made all six locales technically supported (translation infrastructure, taxonomy translations, formatting) from V1 — this section only pulls the **switcher's own visibility** forward to match, and defines the fallback behavior so partial translation coverage in TR/DE/ES never breaks the UI.
