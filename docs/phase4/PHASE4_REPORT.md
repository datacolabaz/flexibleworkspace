### P4-8 Admin module — what's in

- **Search everywhere** (`GET admin/search`) — single query box across bookings/payments (exact UUID), providers, rooms, customers (§18/§33's "Search Everywhere").
- **Audit log browsing** (`GET admin/audit-log`) — filterable by entityType/entityId/actorUserId/action, gated by `AdminPermission.AUDIT_READ`.
- **User management** (`admin/users/*`) — search/list/view, narrow-allowlist display-field correction, suspend/reinstate — all through `AdminPermission.USER_READ`/`USER_UPDATE`/`USER_SUSPEND`.
- **Cross-provider listing correction + revert** (`admin/rooms/:id`, `admin/rooms/:id/revert/:auditLogId`) — a narrow correctable-field allowlist (not the full owner-facing room input), every correction reason-required and audited, and a **revert-as-new-audit-event** implementation of §33.7: reverting re-applies the prior values through the same `correctRoom()` path rather than editing the original `audit_log` row, so a revert is itself a fully audited correction linked via `revertedAuditLogId`.
- **Taxonomy/master-data management** (`admin/taxonomy/room-types`, `admin/taxonomy/amenities`) — the first write path onto what were seed-only reference tables (`room_type`/`amenity`), gated by `AdminPermission.TAXONOMY_UPDATE` on mutations only (see below).

All mutating admin actions go through the single `AuditLogService.recordChange`/`recordRevert` path (§33.6) — never a bespoke audit write per controller.

**Design decision — revert is per-entity-type, not generic.** A single "replay `beforeState` via raw `UPDATE`" endpoint would be unsafe: different entities have different safe-undo semantics (e.g. a Payout's `PAID -> AVAILABLE` isn't a field patch, it's `PayoutsService.reverse()`'s own ledger-clawback flow). Room correction is the first of what should become one revert path per correctable entity, added as each entity gets an admin-correction surface.

**Design decision — taxonomy read permission.** The approved permission matrix (§33.4) defines `taxonomy.update` but no read-side permission (unlike the `listing.read`/`listing.update` pair elsewhere). Reference data (room categories, amenities) isn't sensitive, so `GET` routes are left open to any admin role rather than inventing an ungranted permission; only the four mutating routes are gated behind `taxonomy.update`.

### Known limitations / explicitly deferred (not gaps — scoped decisions)

These were deliberately left out of P4-8 rather than built against invented schema or against a module that doesn't exist yet:

1. **CMS (banners/FAQ)** — no approved DDL exists for CMS content. Building it now would mean inventing new tables outside the Phase 2 schema without a product decision. Needs a schema addition + product sign-off before implementation.
2. **System settings (feature flags / maintenance mode)** — same reasoning: no approved key-value settings table in `28_DATABASE_DDL.sql`.
3. ~~Partner admin management~~ — **done, see P4-3a below.**

None of these block P4-9/P4-10 (frontend) or the rest of the backend — they're additive surfaces, not dependencies of anything already built.

### P4-3a Partner/Referral module — what's in

Implements `31_PARTNER_REFERRAL_ARCHITECTURE.md` end to end: the `partner`/`referral_campaign`/`referral_click`/`booking_referral_attribution` tables (already created by migration `1700000000003-PartnerReferral.ts`, applied before this pass — no new migration was needed) now have entities, services, and controllers on top of them.

- **Public tracking** (`GET /r/:code`, excluded from the versioned API prefix so partner links stay short) — records a server-side `ReferralClick`, sets an opaque `httpOnly`/`Secure`(prod)/`SameSite=Lax` cookie, redirects to the marketplace. An unknown code, a paused/ended campaign, or a suspended partner all resolve to a plain redirect with no cookie set, never an error page. Rate-limited (30/min) as the V1 fraud mitigation §31.7 calls for. The redirect's optional `?to=` landing path is sanitized against open-redirect payloads (`//host`, `javascript:`, etc.) — an addition beyond what the architecture doc specifies, since a public redirect endpoint is a natural target for that class of abuse.
- **Booking-time attribution** (`BookingsService.create`) — reads the attribution cookie, and inside the *same transaction* as the booking/booking-item insert, verifies it against a real, unexpired `ReferralClick` row (re-checking the campaign and partner are still active at booking time, not just at click time) before writing `BookingReferralAttribution`. Every failure mode — missing/garbage token, expired click, ended campaign, suspended partner, a race producing a duplicate write — is a silent no-op, never a reason the booking itself fails.
- **Commission/ledger hook** — already existed from the P4-5 pass (`CommissionService.buildPartnerCommissionEntry`, written ahead of time against the raw tables); this pass is what makes it fire for real, since attribution rows now actually get created. Verified end to end in tests: confirmed booking → `PARTNER_COMMISSION` ledger entry → refund → proportional `REFUND` reversal that nets the partner's ledger to exactly zero. `PROVIDER_NET` is untouched by any of it (§31.3's central invariant).
- **Payout machinery** — `PayoutsService`'s generic `provider_id`/`partner_id` design (built in P4-6) needed zero changes; a partner's eligible `PARTNER_COMMISSION` batches into a real `Payout` and reaches `PAID` exactly like a provider payout. Added `notifyPartnerPaid` (mirrors `notifyProviderPaid`) — but see the FK note below.
- **Admin CRUD** (`admin/partners/*`, all admin-provisioned per §31.7 — no self-signup) — create/list/update partners, `PENDING→ACTIVE`/`ACTIVE↔SUSPENDED` status transitions (gated by `partner.approve`, separate from ordinary field edits on `partner.update`), campaign create/list/update, and `GET admin/partners/:id/analytics` (clicks, attributed bookings, commission available/pending/in-transit/paid — reuses `PayoutsService.getBalance` rather than re-deriving the eligibility math).
- Every admin mutation goes through `AuditLogService`, same discipline as P4-8.

**Real conflict found and resolved — partner payout-paid notifications.** `notification.user_id` is `NOT NULL REFERENCES app_user(id)` (a real FK, `28_DATABASE_DDL.sql` §10), and `Partner.ownerUserId` is a reserved, nullable column that no V1 partner ever has set (§31.7: no self-service partner portal exists yet). Sending through `NotificationsService.send()` for a partner with no linked `app_user` would violate that FK on **every** real V1 partner, not an edge case. Rather than fabricate a `user_id` or bypass the notification table (losing the delivery-record guarantee §17.5 exists for), `notifyPartnerPaid` now no-ops with a log line until a partner has an owner account; until the self-service portal ships, the admin payout statement (already complete, §14.5 step 4) is how ops confirms a payout to a partner. This is a genuine schema-level constraint, not a guessed business rule — flagging it here rather than silently working around it.

**Brand-name discipline (per the conversation record).** The marketplace's public name/domain are not finalized. Nothing in this module hardcodes one: `partner.publicBaseUrl` config (env `PARTNER_PUBLIC_BASE_URL`) defaults to the literal placeholder `[MARKETPLACE_DOMAIN]`, used only to build a convenience `trackingUrl` string in admin API responses — the `/r/:code` route itself works correctly regardless of this value. `FlexSpace` stays as the internal/dev-only codename (folder name, `package.json`, DB name, default SMTP domain) per explicit instruction — not touched, not expanded.

**Deferred, and why (brand-dependent, explicitly out of scope for this pass):**
- **Partner-facing landing page / self-service portal / marketing kit** — §31.7 already scopes this out of V1 (partners are admin-provisioned, `Partner.ownerUserId` is reserved-but-unused). Building the partner-facing pieces (a public "become a partner" page, downloadable logo/brand assets, campaign templates) needs the marketplace's actual name, logo (SVG/PNG, light/dark/mono variants), brand colors, and typography — none of which exist yet. This is pure addition on top of what's built now, not rework.
- **Partner dashboard (self-service analytics)** — same §31.7 V1 scope line; `GET /admin/partners/:id/analytics` already computes everything a future partner-facing version would need, it's just admin-only for now.

## Fixed since last verification pass

**`cookie-parser` boot crash (disclosed in the prior environment-verification report) — fixed.** Root cause was `import cookieParser from 'cookie-parser'` compiling, under this project's `tsconfig.json` (`allowSyntheticDefaultImports` without `esModuleInterop`), to a `.default` property access that doesn't exist on that plain-CJS package. The first fix attempted — adding `esModuleInterop: true` repo-wide — was reverted: it broke `import * as request from 'supertest'` in `test/app.e2e-spec.ts` and `test/partners.e2e-spec.ts` (a wider blast radius than the one crash site). The actual fix applied is scoped to the one import: `src/main.ts` now uses `import cookieParser = require('cookie-parser')` (TypeScript's CommonJS-specific import form, unaffected by `esModuleInterop`), leaving every other file's compiled output unchanged. Verified: `tsc --noEmit` clean, `nest build` + `node dist/main.js` boots for real and serves real HTTP requests (confirmed `helmet()` headers present and `GET /r/:code` returns a real 302 with security headers), 23/23 unit tests, 79/79 e2e tests — no regression from either the fix or the reverted first attempt.

**i18n — done.** `next-intl`, locale-prefixed routing for all six locales (`az` default), `az`/`en`/`ru` fully translated, `tr`/`es`/`de` deep-merge onto the English messages so a missing key falls back to English rather than a blank string or raw key (`20_I18N.md` §20.7's requirement). Verified against the running app, not just by inspection: `/az`, `/en`, `/ru` each render their own translated homepage copy; `/tr` renders its one translated nav string and falls back to the English subtitle; bare `/` redirects to `/az` with all six `hreflang` alternates present.

**OpenAPI client — done.** `openapi-typescript` generates `lib/api-client/schema.d.ts` directly from `docs/phase2/29_API_OPENAPI.yaml` (`npm run generate:api`, never hand-edited) — the same drift-prevention discipline ADR-003 already applies backend-side. `lib/api-client/client.ts` is a thin `openapi-fetch` wrapper: per-request client (no module-level singleton, so one request's bearer token can't leak into another's), an `ApiError` that carries the backend's `{error: {code, message, details}}` envelope, and `import 'server-only'` so it's a build error to import it into a Client Component. `lib/api-client/rooms.ts` (`searchRooms`, `getRoomDetail`) is the reference example other feature code will follow. **Explicitly not TanStack Query** — the go-ahead said start with RSC + native fetch and only add it later against a concrete requirement; nothing in this pass needed it.

**BFF/auth foundation — done.** Go-ahead item 10: Route Handlers that call the NestJS backend and re-set its body-returned token pair as this origin's own `httpOnly` cookies, so a page script can trigger login/refresh/logout but never read the tokens afterward. Four routes in `app/api/auth/`, all built on the generated client (`lib/api-client/client.ts`) — zero backend changes:
- `otp/request/route.ts` — validates `identifier`, calls the backend, returns a bare `204`. No cookies touched.
- `otp/verify/route.ts` — validates `identifier`+`code`, calls the backend, and on success sets `spotva_access_token` (maxAge from the backend's own `expiresIn`) and `spotva_refresh_token` (maxAge hardcoded to 30 days, mirroring the backend's `JWT_REFRESH_EXPIRES_IN` default since the response doesn't expose it — flagged in code as needing manual updating if that default changes) — both `httpOnly`, `secure` in production, `sameSite: 'lax'`. Response body is only `{success: true}`; tokens never appear in JSON.
- `refresh/route.ts` — reads the refresh cookie from the request itself (never from a client-supplied body); `401`s immediately with no backend call if absent; on success rotates both cookies (the backend already invalidates the old refresh token server-side per its own rotate-on-use design); on a backend rejection, clears both cookies rather than leaving a dead session's cookie behind, so the frontend doesn't keep retrying against it.
- `logout/route.ts` — best-effort calls the backend's `/auth/logout` to revoke the refresh token server-side, but clears this origin's cookies and returns `{success: true}` unconditionally, including when the backend call throws — a user must always be able to log out locally even during a backend outage. Skips the backend call entirely if there's no refresh cookie to send.

`lib/auth/cookies.ts` centralizes cookie names and options (a local `CookieOptions` interface, not a deep Next internal-path import that was tried and reverted). `lib/auth/session.ts` reads the refresh token from a request's cookie jar behind `server-only`. `lib/auth/route-helpers.ts`'s `apiErrorResponse` converts a caught `ApiError` into a matching-status JSON envelope, and turns anything else into a `502 BFF_INTERNAL_ERROR` without leaking internals.

**Contract drift found and fixed while building this (`docs/phase2/29_API_OPENAPI.yaml`, doc-only, backend code untouched):** cross-referencing the spec against the real, already-shipped `AuthController`/`AuthService` (23/23 unit, 79/79 e2e passing) turned up four discrepancies, all corrected with inline comments citing the drift rather than worked around in the frontend:
1. `/auth/logout` existed in the controller but was entirely missing from the spec — added it.
2. `/auth/otp/request`'s documented response was `200`, but the controller is `@HttpCode(204)` — fixed to `204`.
3. `/auth/otp/verify` was missing the `404`/`429` responses `AuthService.verifyOtp` can actually throw; `/auth/refresh` was missing the `401` `refreshTokens` can throw. Added both.
4. `AuthTokens` had no `required:` array, so the generated types made `accessToken`/`refreshToken`/`expiresIn` all-optional — a real compile error against code that treats them as required (matching the backend's actual `TokenPair` interface). Added `required: [accessToken, refreshToken, expiresIn]`.

This is exactly the protection a generated-from-spec client is meant to provide — caught at compile time, not at runtime against a real user's cookies.

- `Alert.tsx` — `error`/`success`/`warning`/`info`; urgent variants use `role="alert"` (`aria-live="assertive"`), the other two `role="status"` (`aria-live="polite"`) — §7.7's aria-live requirement for async state changes, built once instead of per feature.

Fully controlled (`value`/`onChange`, no internal state) so the parent form stays the single source of truth. Not in §6's named list, but the same "primitive with no business logic" contract as the others — it emits a code string, nothing about auth.

**One real bug caught by the primitive's own unit tests, before it ever reached the feature.** `OtpInput`'s "are all six boxes filled" check was originally `!code.includes('')` on the *joined* code string — but `"123456".includes('')` is `true` for any string (the empty string is trivially a substring of everything), so that check could never pass and `onComplete` would never fire. `tests/otp-input.test.tsx`'s "calls onComplete once all six are filled" test failed immediately on first run (`0` calls, not `'123456'`), which is exactly what a component-level test is for — caught and fixed (check `nextDigits.every(d => d !== '')` on the per-box array instead) before it reached `LoginForm` or a person's browser.

**Login/OTP UI.** `components/features/auth/LoginForm.tsx` (Client Component; `app/[locale]/(customer)/login/page.tsx` is the thin async Server Component wrapping it for `setRequestLocale`/`generateMetadata`) — a two-step flow against the BFF routes from the section above, calling `/api/auth/otp/request` and `/api/auth/otp/verify` by same-origin `fetch`, never the backend or the `server-only`-guarded API client directly (a Client Component can't import that module — Next enforces it as a build error):
- **Identifier step** — email/phone field, client-side "is it non-empty" check before ever touching the network (the real validation is still the BFF's/backend's), `Button isLoading` while the request is in flight.
- **Code step** — `OtpInput`, auto-submits via `onComplete` once all six digits are present (no separate button press needed, though the "Verify and log in" button is still there and works standalone), auto-focuses the first box on entering this step, a 30-second resend cooldown (countdown text, disabled button), and "use a different email or phone" to go back.
- **Error handling** — `components/features/auth/otp-error-messages.ts` maps every backend/BFF error code (`VALIDATION_ERROR`/`INVALID_JSON`, `OTP_INVALID_OR_EXPIRED`, `OTP_TOO_MANY_ATTEMPTS`, `RATE_LIMITED`, `USER_NOT_FOUND`, and an unmapped-code/network-failure fallback) to a translated message, and classifies each as either a field-level error (shown inline under the identifier/code input — "something's wrong with what you typed") or a page-level `<Alert>` banner (shown for throttling/account-level conditions where retyping won't help: rate limits, too-many-attempts, account-not-found). Kept as a pure function, unit-tested on its own without rendering anything.
- **Translations** — a new `auth.login` namespace, fully translated in `az`/`en`/`ru` (the three content-active locales, matching the scaffold's existing pattern); `tr`/`es`/`de` deliberately untouched, so the whole namespace falls back to English string-by-string through the existing deep-merge in `lib/i18n/request.ts` — verified live (`curl http://localhost:3000/tr/login` renders the English title, confirming the fallback covers a namespace that didn't exist yet when that merge logic was written, not just individual keys within an existing one).

### Booking flow (`POST /bookings` → `POST /payments` → payment confirmation) — done

The Room Detail milestone's own "Not yet done" pointed here explicitly ("Booking creation itself... explicitly the next milestone"), confirmed by the go-ahead to proceed. Scope: booking creation (guest or authenticated), hosted-checkout payment initiation, and the two payment-confirmation screens the backend's own config already contracts for.

**Three OpenAPI doc-drift fixes found and fixed while researching the real contracts (again all doc-only — see the OpenAPI drift precedent from every prior milestone):**
1. **`POST /bookings`'s request schema falsely required `customer`.** `CreateBookingDto.customer` is `@IsOptional()` — it's only conditionally required, and only at runtime (an unauthenticated caller without `customer.email`/`customer.phone` gets a 400 `CUSTOMER_REQUIRED` from `BookingsService.create` itself, not from request validation). Removed from the schema's top-level `required` array; documented the real conditional rule inline instead.
2. **`BookingSummary` didn't match what the endpoints actually return.** The schema had a single `room` (a full `RoomSummary`) and top-level `startAt`/`endAt`, with `grossAmount`/`serviceFeeAmount`/`totalAmount` each as separate `Money` objects. The real shape — `BookingsService.create`/`findById`/`listForCustomer` all return the raw `BookingEntity` plus its `items` relation — has none of that: one shared `currency` column, three plain integer amount columns, and the room id/time range living per line-item on `booking_item` (`items[]`), not on the booking itself. Rewritten to match.
3. **`GET /bookings/{bookingId}`'s docs didn't reflect its new optional-auth behavior** (see the backend gap below) — added a `description` explaining the guest-access rule so the next reader of this spec doesn't have to rediscover it from the controller's own comment.

`schema.d.ts` regenerated via `npm run generate:api` after all three edits; `tsc --noEmit` clean immediately after.

**Backend gap found and fixed: `GET /bookings/:bookingId` couldn't actually serve the case it exists for.** Found while building the payment-confirmation page. The backend's own `payments.successUrlTemplate`/`errorUrlTemplate` config (`13_PAYMENT_ARCHITECTURE.md` §13.3) already commits to redirecting every payer — guest or authenticated — to `{CORS_ORIGIN}/booking/{bookingId}/{confirming,failed}`, and `PaymentsService.createCheckoutSession`'s own code comment already documents "possession of the booking's opaque UUID is the gate" for a guest caller looking up their own booking's payment. But `BookingsController.getOne` (`GET /bookings/:bookingId`) still required hard authentication with an ownership check — meaning a guest who just paid, who by definition has no JWT (`AuthService.ensureUser()` provisions a user account for guest checkout without ever issuing one), could never reach the confirmation page's data. Fixed to match the guarantee `PaymentsService` already assumed: `@Public()` with an optional `@CurrentUser()`, enforcing the ownership check only when the caller is authenticated (a non-owning authenticated caller still 404s, never revealing the booking exists). New `bookings.controller.spec.ts` (3 tests: anonymous access, owning-authenticated access, non-owning-authenticated 404) plus a full backend re-verification (typecheck, lint, `nest build`, 26/26 unit, all e2e suites) — no regression.

**Design decisions:**
- **No payment-provider picker in the UI.** `13_PAYMENT_ARCHITECTURE.md` §13.4 names Epoint the V1 primary provider and Payriff a secondary/backup adapter only — which gateway processes a card isn't a decision a customer should have to make, so `BookingForm` always requests `provider: 'EPOINT'`. (Both adapters have an identical dev-mode fallback when uncredentialed, so this didn't limit what could be smoke-tested — see below.)
- **Booking creation and payment initiation are one submit, but retry-safe.** The go-ahead's own task breakdown treated "build the booking form" and "wire payment initiation" as separate steps, but from the customer's side they're one action — `BookingForm` calls `POST /bookings` then immediately `POST /payments` with the returned id. If the booking succeeds but the payment call fails (network blip, provider hiccup), the created booking's id is kept in component state and a retry re-calls only `/api/payments` — never a second `POST /bookings`, which would open a second, redundant hold.
- **`/booking/{bookingId}/{confirming,failed}` are deliberately NOT locale-prefixed.** This isn't a frontend choice — it's the backend's own `payments.successUrlTemplate`/`errorUrlTemplate` defaults (confirmed unmodified in `backend/.env`), which build the exact literal path `{CORS_ORIGIN}/booking/{bookingId}/confirming` with no locale segment. The frontend route lives outside `app/[locale]/` as a third independent Next.js root layout (`app/booking/layout.tsx`, alongside the existing `/admin` and `/provider` precedent), and `middleware.ts`'s matcher now excludes `/booking` the same way it already excluded `/admin`/`/provider` — without that exclusion, next-intl's own middleware would 307-redirect a payment gateway's hosted-checkout callback to a locale-prefixed URL nothing serves.
- **Locale on that unprefixed branch resolves from a cookie, not the URL.** `lib/i18n/resolve-locale.ts` reads the `NEXT_LOCALE` cookie next-intl's middleware already sets on every locale-prefixed page visit (its default `localeCookie` behavior) — present for the overwhelming majority of real visits, since the booking flow always starts on a `/{locale}/...` page. Falls back to `routing.defaultLocale` (`az`) for a cold visit with no cookie (verified live — see below).
- **The confirming page polls, it doesn't trust the redirect.** `PaymentsService.handleWebhook`'s own doc comment is explicit that only the webhook confirms a booking, never the redirect (`13_PAYMENT_ARCHITECTURE.md` §13.3 steps 4-5) — the dev-mode checkout fallback in particular redirects here immediately, well before any webhook fires. `BookingConfirmingView` polls `GET /bookings/{bookingId}` every 3s, shows a "this is taking longer than usual" message past 20s without erroring, and stops on any terminal status (`CONFIRMED`/`COMPLETED`, or a cancelled/expired branch).
- **The failed page re-checks the booking rather than assuming it's dead.** `payments.errorUrlTemplate` fires on a failed/cancelled checkout attempt, before any webhook — the booking's hold (`holdMinutes`) may still be live. `BookingFailedView` fetches the real status and offers same-booking payment retry (`POST /payments` again, no new booking) when still `PENDING`/`PAYMENT_PENDING`, or a "book again" link back to the room when the hold has actually lapsed.

**Two real bugs caught live, both in `AvailabilityService`, both invisible to any unit or e2e test because every existing fixture books far in the future — this milestone's own booking form is the first caller that naturally offers "book starting right now":**
1. **The earliest-bookable instant was a moving target.** `getOpenWindows` (never cached, recomputed fresh on every call — `12_RESERVATION_ENGINE.md` §12.1) clamps a window's start up to `now + advanceBookingMinHours`. For a room with `advanceBookingMinHours = 0` (both seeded rooms), that's effectively "now" — and `BookingWidget` naturally offers that exact instant as its first, most obvious start-time option. Any normal elapsed time between fetching availability and submitting (picking a duration, typing a guest email) meant the backend's own fresh re-validation (`isRangeAvailable`, which reuses `getOpenWindows`) saw a *later* "now," reclamped the window's start past the originally-chosen instant, and rejected an entirely legitimate booking with `SLOT_UNAVAILABLE` — 100% reproducible, caught on the very first live run. Fixed on both sides: `AvailabilityService` now adds a fixed `BOOKING_REQUEST_GRACE_MS` (5 min) network/processing-latency tolerance on top of `advanceBookingMinHours`; `BookingWidget` separately pads the earliest *offered* start time by `START_TIME_LEAD_BUFFER_MINUTES` (10 min) so normal form-fill time doesn't approach either boundary. The residual case (a visitor who sits on the form for several minutes) still gets a real `SLOT_UNAVAILABLE`, now correctly rare rather than universal — handled by the existing, worded error state with a link back to pick again, not chased further.
2. **A window could be offered that no longer fit the minimum booking duration.** `getOpenWindows`'s minimum-duration filter ran *before* the advance-booking clamp, not after — so a window that was comfortably long pre-clamp (e.g. from midnight up to an existing booking later that day) could survive the filter, then get shrunk by the clamp to a sliver narrower than `minBookingMinutes`, and still be returned as an apparently-selectable window with zero actual valid start times inside it. Caught live once a room had one real active booking to split its day window against (the smoke test's own second booking attempt). Fixed by moving the minimum-duration filter to run after the clamp, against the bounds actually returned.

Neither bug is specific to the booking flow's own new code — both live entirely inside `AvailabilityService`, which the Room Detail milestone's `BookingWidget` already called — but neither could have surfaced there, since browsing availability never submits a booking against the literal earliest instant the way this milestone's form is the first to do.

That page already handles same-booking payment retry vs. the expired-hold branch; re-solving it here would just be a second, divergent copy.

**One real bug caught live, in `BookmarkButton` — not exercised by any prior caller of this component.** Both of `BookmarkButton`'s existing callers (room detail page, `/account/favorites`'s `FavoriteRoomCard`) resolve `initiallyFavorited` *before* the button ever mounts (an SSR check, or a hardcoded `true`), so `useState(initiallyFavorited ?? false)`'s one-time initializer was always correct. `SearchResultsView`'s new background check is the first caller where that prop changes *after* mount — result cards render (and `BookmarkButton` mounts) as soon as `/api/search` resolves, then `initiallyFavorited` flips from `false` to `true` only once the separate `/api/favorites` call resolves afterward. Regression-tested directly (`bookmark-button.test.tsx`: adopts a late `true` after mounting `false`; a late value arriving after a click does not undo the click) rather than only through the search-results integration test, since the bug lives in `BookmarkButton` itself and the room detail/`/account/favorites` callers must keep working unaffected (confirmed — neither passes a changing prop, so neither is affected by the fix; their existing tests still pass unmodified).

### Maps provider switched from Google Maps to Mapbox

Post-deployment change: real Google Maps credentials were never available in this project (`PHASE4_REPORT.md`'s own prior notes on `SearchResultsMap`/`RoomLocationMap` flagged this — the code was written against Google Maps JS API but never live-verified against a real key). A real Mapbox public token became available instead, so rather than leave the map placeholder-only indefinitely, the map integration was swapped to Mapbox GL JS, which the real credential actually works against.

**What changed:**
- `lib/maps/loadGoogleMaps.ts` → `lib/maps/loadMapbox.ts`: same lazy-load-on-mount, memoize-the-promise shape, now a dynamic `import('mapbox-gl')` instead of a hand-written `<script>`-tag loader (Mapbox GL ships as an npm package with its own bundled TypeScript types — no separate `@types` package, no loader script needed).
- `RoomLocationMap.tsx` and `SearchResultsMap.tsx`: rewritten against the Mapbox GL API (`mapboxgl.Map`, `mapboxgl.Marker`, `mapboxgl.NavigationControl`). Coordinate order flipped from Google's `{lat, lng}` object to Mapbox's `[lng, lat]` tuple at every call site — noted inline in the code since it's an easy transposition bug otherwise. `cooperativeGestures` (Mapbox's equivalent of Google's `gestureHandling: 'cooperative'`) carried over on the room-detail map.
- `SearchResultsMap`'s highlighted-marker treatment (synced with the results list, §8.6) changed from Google's built-in `Animation.BOUNCE` (no Mapbox GL equivalent) to a custom marker element (`.spotva-map-marker` / `.spotva-map-marker--active` in `globals.css`) whose active state is a CSS class toggle — a plain accent-colored dot that scales up and raises z-index when hovered/selected, rather than a bespoke pin icon set.
- Env var renamed `NEXT_PUBLIC_GOOGLE_MAPS_BROWSER_KEY` → `NEXT_PUBLIC_MAPBOX_TOKEN` throughout (`.env.local.example`, both map components). Both are equally safe to expose to the browser (Google's is HTTP-referrer-restricted in Cloud Console; Mapbox's `pk.` token is meant to be URL-restricted in the Mapbox account's token settings) — same "public, not secret" status, just a different provider's convention.
- `package.json`: added `mapbox-gl` as a real dependency, removed the now-unused `@types/google.maps` dev dependency.

**Verification performed:** `npx tsc --noEmit` clean, `npx eslint .` clean, `npx vitest run` — 196/196 still passing (no regression; neither map component had dedicated tests before or after this change — same gap as the original Google Maps implementation, carried forward under the new provider, not newly introduced), `npm run build` succeeds. **Not verified:** live-rendered map tiles/markers in a real browser — same "no browser can reach this sandbox's dev server" limitation noted throughout this document's frontend sections; the placeholder-degradation path (no token set) is structurally identical to the Google Maps version's, which was live-verified earlier in this document.
